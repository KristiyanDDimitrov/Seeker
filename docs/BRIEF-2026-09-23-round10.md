## §1 — Review page: Confirm on a SoulSeek candidate "does nothing"

### What Kris saw

On the Review page, a SoulSeek needs-review candidate. Clicking
**Confirm** does not remove it. Instead, each click highlights the next
cell of that row in turn: track, then score, then candidate, and so on.
Clicking again repeats this. **Reject** works. Kris has seen this
before.

### What is established

There are three separate defects here. They look like one bug because
they happen together.

**Defect A. Confirm is failing, and the error goes to a label that
cannot be seen.**
`ReviewPage._on_confirm_review_candidate` (`ui/pages/review_page.py:
435-450`) runs `download_service.confirm_review_candidate` in a worker
with `status_label=self._host.status_label`. `ReviewHost.status_label`
is wired in `main_window.py:706-714` to
**`self._dashboard_page.status_label`**, a widget on a different page.
When the worker raises, `_handle_task_error` (`ui/workers.py:457-481`)
re-enables the button and writes the message into the Dashboard's
label. Kris is on the Review page, so he sees nothing. `on_finished`
never runs, the table is never re-polled, and the row stays.

All five `run_worker` calls on the Review page do this (lines 448, 462,
644, 747, 761). So does `_on_upgrade_decision_finished` (line 619),
which writes the *success* message there. No other page does it.
Library/Tagging, Search, Sharing, Duplicates, and History all route to
widgets on their own page (checked with `grep -n "status_label="` over
`ui/`).

This is also the exact failure that `ui/notice.py`'s module docstring
describes as the reason `InlineNotice` exists: `run_worker` clears its
`status_label` to `""` at the start of every call (`workers.py:529-530`),
and the Dashboard's poll reuses that same label every 2 s. So a message
on that label would be wiped within ~2 s even if Kris were looking at
it.

**Defect B. Worker exceptions are never logged.**
`Worker.run` (`workers.py:198-216`) catches `Exception` and emits only
`str(error)`. There is no `logger` call and no traceback.
`~/Library/Logs/Seeker/seeker.log` confirms this: it is 442 bytes, and
its last entry is dated 2026-09-10. Every failed confirm since then
left no trace anywhere. This is why the bug is undiagnosable from the
log, and why it "came back" without anyone noticing.

**Defect C. The cell highlight that moves one column per click is Qt
focus traversal, not a rendering bug.**
The mechanism, from Qt's source:
1. The click gives the Confirm `QPushButton` keyboard focus. Fusion is
   applied (`apply_theme`), so buttons are `StrongFocus`.
2. `run_worker` calls `button.setEnabled(False)` (`workers.py:526-527`).
3. When a focused widget is disabled, Qt calls `focusNextChild()` on it
   (`QWidgetPrivate::setEnabled_helper`).
4. `QWidget::focusNextPrevChild` on a non-window widget forwards to its
   parent. It walks from the cell-widget container, to the viewport,
   and then to the `QTableWidget`.
5. `QAbstractItemView::focusNextPrevChild`, with `tabKeyNavigation` on
   (the default), synthesises a **Tab key press**, which moves the
   current index one cell to the right.

So each click moves the highlight one column, exactly as Kris saw.
Reject does the same thing, but its row disappears on success, so no
one ever noticed. **This affects every table that uses
`theme.cell_widget`** (`theme.py:360`, 15 call sites), not only Review.

### What is NOT yet established: why the confirm raises

`confirm_review_candidate` (`soulseek/download_service.py:748-808`) can
raise for three known reasons:

1. **`ReviewCandidateMissingSizeError`**: a legacy row with
   `size IS NULL`. HISTORY (search `ReviewCandidateMissingSizeError`,
   ~line 2855) records two such real rows from item 17: *Prdk – ONE MORE
   NIGHT* (70.4) and *Zigi SC, A-Cray – Bit Perfect* (73.2). Neither was
   ever confirmed or rejected at that time. This fits "I've encountered
   this before" best.
2. **Peer offline or file no longer shared.** `SoulseekClient.
   request_download` (`soulseek/client.py:130-170`) turns slskd's
   synchronous 404 *"User X appears to be offline"* into
   `SoulseekDownloadError`. A candidate found weeks ago can easily have
   an offline peer.
3. **slskd not reachable**: a connection error.

Do not guess which one it is. §1.4 decides it.

### The fix

**§1.1 — Cell-widget buttons must not take focus.** In
`theme.cell_widget`, set `Qt.FocusPolicy.NoFocus` on every
`QAbstractButton` passed in. Nothing is lost for keyboard users: with
`tabKeyNavigation` on, Tab already moves between cells and never enters
cell widgets. **Test first:** build a `QTableWidget` with 3 text columns
and a `cell_widget(button)` in column 3. Set current cell (0, 0). Click
the button with `qtbot.mouseClick` (a real click, which is what gives
focus). Disable the button the way `run_worker` does. Assert that the
current column is still 0. This must fail on `HEAD` because the column
moves to 1. One commit.

**§1.2 — Review gets its own notice. Nothing on Review writes to the
Dashboard's label again.**
- Add `self.notice = InlineNotice()` at the top of the Review page's
  content, following the Library/TaggingPanel precedent (look at
  `library_page.py:59-72` and how `tagging_panel.py` uses
  `notice.show_message(..., kind="error")`).
- All five Review `run_worker` calls: drop `status_label=`, and pass
  `on_error=lambda message: self.notice.show_message(message,
  kind="error")`. `_on_upgrade_decision_finished` and the bulk-replace
  result go to the notice as `kind="info"`/`"success"`, whichever
  `_VALID_KINDS` has.
- Remove `status_label` from `ReviewHost` entirely (`review_page.py:
  90-96`, `main_window.py:709`). A field nobody should use is a trap.
  Update the module docstring that describes it.
- Rewrite `test_review_tab_replace_button_calls_apply_upgrade_decision_
  with_delete_flag` and the decline test (`tests/pages/
  test_review_page.py:191-212`, `~265-285`) to assert on
  `window._review_page.notice`. **Wait on the notice text itself**
  (`qtbot.waitUntil(lambda: notice.text() == ...)`), not on the fake's
  call list. See §4 for why that difference is the CI flake. The
  decline test must assert that the notice is still hidden *after*
  on_finished has provably run. Today it asserts `""` immediately,
  which passes whether or not anything happened (vacuous).
- New test: the Confirm worker raises → the Review notice shows the
  message as an error, and the row is still there.
- One commit.

**§1.3 — Log worker failures with a traceback.** In `Worker.run`'s
`except` block, call `logger.warning("Background task %d failed",
self.task_id, exc_info=True)` **before** `_emit_or_drop`. Worker
threads are where the traceback exists. `logging` is thread-safe. Read
the straggling-worker comment right above that line first: logging
must not add a new failure mode at teardown, so the call must not
touch `_dispatcher` or any Qt object. A test that uses `caplog` asserts
the traceback is recorded. One commit. Keep this separate from §1.2,
because `workers.py` is the file with the deadlock history, and it
must be revertable on its own.

**§1.4 — Diagnose the real stuck candidate. Read-only. No code
commit.**
- `sqlite3 -readonly ~/Library/Application\ Support/Seeker/seeker.db
  "select track_id, username, filename, size, score from
  soulseek_review_candidates"`. Check the column names against
  `database/schema.py` first. Name the row or rows, and flag
  `size IS NULL`.
- For each row with a size: is slskd up, and is the peer online? Use
  slskd's own user-status endpoint if one exists. **Verify the endpoint
  against the live slskd before relying on it.** Do not call
  `confirm_review_candidate` yourself. If it succeeds, it starts a real
  download and moves a file into Kris's library.
- If §1.2 and §1.3 are already in the build, the fastest ground truth
  is Kris clicking Confirm once. The notice shows the message and
  `seeker.log` gets the traceback. Ask for this in the handoff if the
  read-only checks do not settle it.
- Write the finding into the handoff as a root-cause statement with
  the raw query output. §2 is built on it.

## §2 — Make Confirm actually work for the cause §1.4 found

Only after §1.4. Pick the branch that matches the evidence:

**If `size IS NULL` (legacy row):** the current error message tells
Kris to re-download the whole playlist to refresh one row. That is not
acceptable as the answer to a button press. The fix is to resolve the
size for the exact file the human confirmed, then proceed:
- slskd can list a peer's directory. Find the real endpoint and its
  real response shape **from the live slskd, not from memory or docs**.
  It is likely under `/api/v0/users/{username}/...`. Record the raw
  response in HISTORY. Add a `SoulseekClient` method that returns the
  size of `filename` in its parent directory, or `None`.
- `confirm_review_candidate`: when `candidate.size is None`, resolve it
  first, **write it back to the candidate row** (DB state only, which is
  fine), then proceed as normal. Never guess or default a size.
- If the peer is offline or the file is gone, raise a clear, specific
  error. The row stays, and the notice (§1.2) says what happened and
  that Reject is the way to drop it.
- Tests: the resolve succeeds and the download proceeds with the
  resolved size, and the row is updated. The resolve returns `None` and
  you get the specific error, with no DB mutation.

**If the peer is offline or the file is gone:** the service is already
correct to refuse. The product problem is only visibility, which §1.2
solves. What is left: make the message say *which* peer and *what to
do* ("…is offline right now. Try again later, or Reject to drop this
candidate."). Put the string in `help_text.py`.

**If slskd is unreachable:** the message must say that, not show a raw
`httpx` string. Check how other pages already phrase "slskd not
reachable" and reuse that.

**If it is something else:** root-cause it. Do not widen a `try` to
make it go away.

Live verification: after the fix, Confirm on the real row either
starts the download (the row leaves Review and appears in Downloads) or
shows the specific notice. Paste which one happened, with a screenshot.

## §4 — CI is red on every push: the two "flakes" are one test race

### Established

Round 9 ended with CI red on S7, S8, S9, and S10's pushes, always with
the same pair: `test_history_refresh_button_refetches` and
`test_review_tab_replace_button_calls_apply_upgrade_decision_with_
delete_flag`. They often fire in the same run. Both tests share one
pattern:

1. They `qtbot.waitUntil(...)` on a **fake service's call counter**
   (`get_recent_events_calls == 2`; `apply_upgrade_decision_calls ==
   [...]`).
2. The fakes record the call **at the top of the method, on the worker
   thread** (`tests/test_ui_smoke.py:290-292` and `441-450`), before
   the result is returned. It is returned long before the main thread
   processes the queued `task_finished`.
3. Then the test acts or asserts on a **main-thread effect** that only
   happens once `_handle_task_finished` has run.

For the review test, this is exactly `assert '' == 'Replaced with
/new/path'`: the counter matched, but `on_finished` had not been
delivered yet.

For the history test, the refresh button is still **disabled**
(`run_worker` disables it until `_handle_task_finished` re-enables it,
and `run_busy_worker` also holds the `"history_refresh"` busy key).
`history_refresh_button.click()` on a disabled button is a no-op, so
call #3 never happens. This matches round 9's instrumentation exactly:
both real CI snapshots read `no tasks in flight`, because the click
never submitted anything. A slow macOS runner widens the window, which
is why it is CI-only.

**Hypothesis to confirm, not assume:** that this is the *whole* story
for both tests. The deterministic repro below confirms it or kills it.

### The fix

- **§4.1 Deterministic repro, before any fix.** Make the fake block
  after recording its call: an optional `threading.Event` that the test
  controls, so the counter is visible while `task_finished` is not yet
  delivered. Show that the history test's click is a no-op in that
  window, and that the review assertion reads `''`. Paste both. If it
  does not reproduce this way, stop and report. Do not ship a fix for
  an unconfirmed mechanism.
- **§4.2 Fix the tests, not the product.** A disabled button ignoring
  clicks is correct behaviour. Each test must wait for the
  **main-thread** condition it depends on: for example, the button is
  enabled again and the busy key is released before clicking, or the
  rendered text before asserting. If §1.2 has landed, the review test
  is already rewritten; confirm it is race-free and move on.
- **§4.3 Audit, not just two tests.** There are ~159 `waitUntil` calls
  across `tests/pages/` and `tests/test_ui_smoke.py`. Find every place
  where a `waitUntil` on a fake's `*_calls` is immediately followed by
  a UI assertion or a click on a button that `run_worker` disables. A
  grep plus reading each hit is enough. Fix each one the same way, and
  list them in the report. Consider a small helper in the test
  conftest (for example, `wait_for_workers_idle(window)` that waits for
  `workers._callbacks` to drain) if it makes the fixes one line each.
  Do not add `pytest-rerunfailures`, and do not raise timeouts.
- **Verification:** 20 consecutive local full-suite runs, plus the
  first CI run after the push. Record the run id. CI green is the
  acceptance criterion for this section. If CI is still red, paste the
  failure and name it; do not call it a flake.

Update the two entries in `CLAUDE.md` → Open issues: close them if
fixed, in place, per the documentation rules.

## §5 — Reopen after a fullscreen close: fill the screen, windowed

### What Kris saw, and decided

Kris closes the window while it is fullscreen, then reopens from the
**Dock / menu-bar icon** (same process, not a relaunch). The window
comes back at the default size.

**Decision (Kris, 2026-09-23):** a window closed while fullscreen comes
back **filling the screen as a normal window** (zoomed/maximized on the
same desktop). It does **not** re-enter macOS fullscreen. Re-entering a
fullscreen Space is the transition that produced round 7's empty,
unclosable window (E1), and a start-at-login app that jumps into its
own Space is hostile. A window closed windowed comes back at exactly
its windowed geometry, as now.

### Established

The reopen path is `TrayController._on_tray_open_seeker`
(`ui/tray.py:270-300`). The Dock click reaches it through
`on_application_state_changed` (`tray.py:304-335`). It calls
`showNormal()`, then `setGeometry(_pre_fullscreen_geometry)`. That
value was captured in `closeEvent`'s fullscreen branch
(`main_window.py:2026-2027`) as `self.normalGeometry()`. So today's
design (D4.2) is "come back at the pre-fullscreen windowed size".
If Kris went fullscreen from a window he had never resized, that
**is** the default size. So "working as designed" and "Kris's bug"
can be the same thing. The decision above replaces the design, so
you do not need to prove which of the two it was.

Two related problems on the same path:
- `closeEvent`'s fullscreen branch also **persists** geometry while
  fullscreen (`main_window.py:2034`). `saveGeometry()` then records the
  fullscreen flag, so a later **relaunch** runs `restoreGeometry()` →
  `setWindowState(FullScreen)` before the first show, twice (`__init__`
  and `showEvent`). That is the transition we just decided never to
  make. **Hypothesis:** on a real Mac, this relaunch path is also
  broken. Check it live; it is in scope either way.
- A window closed **zoomed** (Window → Zoom, `_on_zoom_clicked`)
  reopens un-zoomed today, because `showNormal()` clears the state. The
  same fix covers it.

### The fix

- Replace `_pre_fullscreen_geometry` with one piece of state:
  `_reopen_filled: bool`. It is set in `closeEvent` (both branches) as
  `isFullScreen() or isMaximized()`, captured **before** anything
  changes the state.
- One method owns "show the window the way it was closed", for example
  `MainWindow.show_restored()`. If filled, `showMaximized()`; otherwise
  `showNormal()`. `_on_tray_open_seeker` calls it instead of the
  `showNormal` + `setGeometry` pair. `TrayHost`'s
  `get/clear_pre_fullscreen_geometry` go away.
- Persist it for relaunch: add a `window_reopen_filled` field to the
  persisted settings, default `False`. **A `config.json` without the
  key must load unchanged.** Verify by loading Kris's real config
  read-only, and paste the before/after `update_settings` round-trip.
  On restore, after `restoreGeometry()`: if the restored state includes
  `WindowFullScreen`, clear that bit and treat it as filled. Never let
  a restore enter fullscreen. `main_ui.py`'s first `window.show()`
  honours the flag too, so relaunch and reopen behave the same way.
- Keep the round-9 `showEvent` first-show re-apply. Make sure it cannot
  un-maximize a window the flag just maximized. Order it explicitly and
  say how.
- **Offscreen tests assert window *state*, never pixels** (round 9
  §3.1 follow-up 3). Close while `showFullScreen()` → reopen via
  `_on_tray_open_seeker` → `isMaximized()` and not `isFullScreen()`.
  Close windowed after `resize` → reopen → not maximized, with the same
  `normalGeometry().size()`. Zoomed close → maximized reopen. A saved
  blob that carries the fullscreen flag → restore → not fullscreen.
  Rewrite `test_reopening_after_a_fullscreen_close_restores_prior_
  geometry` (`test_ui_smoke.py:3540`) to the new contract. Do not
  delete it.
- **Live verification on the real Mac is the acceptance test.**
  Offscreen Qt is what let the round-9 fix ship broken. Script it:
  System Events can set `AXFullScreen` on `window 1` of process
  "Seeker". HISTORY has prior recipes (`grep -n "AXFullScreen"
  docs/HISTORY.md`), including why the fullscreen close button is not
  in the AX tree. Reopen with `open -a Seeker`, which is a real reopen
  gesture. Read back `size of window 1` and compare it with the
  screen's visible frame. Run all three paths (fullscreen close → Dock
  reopen; windowed resize → close → Dock reopen; fullscreen close →
  quit from tray → relaunch) and paste the raw numbers plus one
  screenshot each. Kris confirms by hand afterwards.

## §6 — The fullscreen-close test pair that fails only in the full suite

### Established, with one hypothesis

`test_fullscreen_close_policy_check_ignores_a_stale_request`
(`test_ui_smoke.py:3849`) and its sibling fail together in the full
suite with `assert dock_calls == []` → `[True]`, and they pass alone.
This has happened three times, with no diagnosis.

`_set_dock_icon_visible(True)` has exactly two callers. The monkeypatch
replaces the module-level function, so it catches calls from **any**
live `MainWindow`, not only this test's window:

1. **`_on_tray_open_seeker`** (`tray.py:283`, through the host). It is
   reached from `on_application_state_changed(ApplicationActive)`
   whenever the window is not visible (`tray.py:331-335`), and the
   window is closed at exactly that point in the test.
   `main_window.py`'s own comment (lines ~419-424) records that
   `applicationStateChanged` **does fire organically from show()/close()
   under offscreen Qt**. Whether it fires during this test's
   `qtbot.wait` depends on the state earlier tests left the
   `QApplication` in.
2. **`cleanup_before_quit`** (`main_window.py:1907`, unconditional). A
   *previous* test's window that is still alive, running its cleanup
   during this test's wait, would also append `True`.

Either one explains the order dependence. **Find out which, do not
assume.** Put a temporary one-line trace in both callers (log `id(self)`
and the stack) and run the full suite until the pair fires. Then
reproduce the guilty path deterministically in isolation. For
candidate 1, deliver `ApplicationActive` through
`window._on_application_state_changed` during the wait. For candidate
2, keep a second window alive and trigger its cleanup. Paste both.

### The fix

Make the tests deterministic, not the product more complicated. For
example, a fixture that pins the app state, or disconnects the app-state
reopen for tests that are not about it. Choose the one that isolates
best, and put it in conftest if more than one test needs it. The
product behaviour (Dock click → reopen) is correct and stays. If §5
rewrote the geometry test, re-check that it is covered. 10 consecutive
full-suite runs without the pair firing is the bar. Update the Open
issues entry in place.
