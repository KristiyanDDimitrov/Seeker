## B2 — No visual separation between column-header cells (global)

**CONFIRMED, with the exact commit that caused it.**

`git log -L '/QHeaderView::section/,+8:src/seeker/ui/theme.py'` shows the
rule was introduced by `2075cba` ("Design system: dark theme +
InlineNotice", roadmap item 47) and has read the same ever since
(`theme.py:432`):

```
QHeaderView::section {
    background-color: {BG_SURFACE};
    color: {TEXT_MUTED};
    border: none;                        /* <- this */
    border-bottom: 1px solid {BORDER};
    padding: 6px;
}
```

`border: none` removes the section's left/right edges, so adjacent header
sections have no divider — while the resize grips still work, which is
exactly the "I can drag it but I can't see it" the user describes. And
once *any* `QHeaderView::section` rule exists, Qt stops drawing the
native header entirely and paints from this box model only, so there is
no fallback separator underneath. The user's "we used to have a faint
greyish line, but it disappeared through the UI polishing" is literally
correct: it disappeared in item 47.

- [ ] **B2.1** Give sections a real right-hand divider in `theme.py`:
  `border-right: 1px solid {BORDER};` on `QHeaderView::section`, keeping
  the existing `border-bottom`. Suppress it on the trailing section
  (`QHeaderView::section:last` — and check the horizontal-only variant
  `QHeaderView::section:horizontal:last-child` renders as intended,
  since Qt's support for these pseudo-states on headers is version-
  dependent). If the `:last` suppression doesn't take, a divider on the
  last section is a cosmetic nit, **not** a reason to abandon the fix —
  ship the dividers and note it.
- [ ] **B2.2 — check the body grid too, with pixels.** `theme.py:401`
  does set `gridline-color: {BORDER}` on `QTableWidget`, and nothing in
  the app calls `setShowGrid(False)` (grep: zero hits). But `make_card()`
  applies a **per-widget** stylesheet to the inner table
  (`inner.setStyleSheet("border: none; border-radius: 0px;")`,
  `theme.py:128`), and whether that widget-level sheet leaves
  `SH_Table_GridLineColor` resolving to the app-level rule is a Qt
  runtime question this environment cannot answer. **Experiment:** with
  a populated Downloads table, `window.grab()` at the default size,
  sample the pixel column between two body cells and report the real RGB
  against `BORDER` (`#3A344E`) and `BG_SURFACE`. If the grid is absent,
  the fix is to move `gridline-color` into `make_card`'s own per-widget
  sheet so it can't be lost.
- [ ] **B2.3** This is a `theme.py`-only change, so it lands everywhere
  at once by construction. Confirm that with real screenshots of at
  least Downloads, Duplicates and Settings → Library Locations, before
  and after.
- [ ] **B2.4** Regression test: assert the stylesheet string contains a
  `border-right` on `QHeaderView::section`. A weak test, but it pins the
  exact property whose removal caused this, which is more than existed

## B4 — The "Queued" progress bar sits at the top of its cell

**CONFIRMED in source, and it is a one-branch inconsistency.**

`_build_progress_widget` (`main_window.py:579`) has three exits. Two of
them wrap the bar in a container:

```python
container = QWidget()
layout = QHBoxLayout(container)
layout.setContentsMargins(0, 0, 0, 0)
layout.addWidget(bar, 1)
layout.addWidget(QLabel(eta_text or "Calculating…"))

```

The indeterminate branch — the one that runs for `queued` — does not:

```python
if not (request.total_bytes and request.bytes_transferred is not None):
```

`setCellWidget` resizes its widget to the full cell rect, and the global
stylesheet caps `QProgressBar { max-height: 14px; }` (`theme.py:~465`).

top; a bar inside a `QHBoxLayout` is centred by the layout. Exactly the
screenshot.

- [ ] **B4.1** Wrap the indeterminate bar in the same container shape as
  the other two branches — `QHBoxLayout`, zero margins,
  `addWidget(bar, 1)` — with **no** ETA label (the existing comment is
  right that there is nothing determinate to estimate). Do not
  special-case alignment with `setAlignment`; matching the other
  branches is what makes it identical, and identical is the point.
- [ ] **B4.2** Extract the container construction into one small helper
  used by all three exits, so a fourth branch can't reintroduce this.
- [ ] **B4.3 — verify with pixels** (5b.3's discipline). Force a real

## B5 — Only download real DJ formats

**CONFIRMED, including the live consequence.**

`quality._score_candidate` gates SoulSeek candidates on
`AUDIO_EXTENSIONS` (`quality.py:52`) — the same set the **library
scanner** uses. That set includes `.ogg`, `.aac` and `.aifc`, so a peer's
`.ogg` is a perfectly acceptable download, and then nothing downstream
can tag it: `metadata.py` only ever branches on `ID3` (mp3/wav/aiff),
`FLAC` and `MP4` (m4a). Hence the reported
`format_unsupported: album art isn't supported for this file format`.

Measured against the real library (3,400+ files under
`/Volumes/X9 Pro/Music`):

```
2027 mp3   1176 flac   144 aiff   68 wav   33 aif   12 m4a
   1 ogg   0 opus   0 wma   0 ape   0 aac   0 mp4   0 aifc
```

The single `.ogg` is the exact file in the user's screenshot
(`Skrillex and Diplo present Jack Ü/Jack Ü, Skrillex, Diplo, Missy
Elliott - Take Ü There (feat. Kiesza) - Missy Elliott Remix.ogg`). Every
other file in the library is already in the taggable set. So the
allowlist isn't a guess — it is what the library already is.

- [ ] **B5.1 — two sets, named for what they mean.** Add to
  `audio_formats.py`:
  ```python
  # What Seeker will INDEX if it's already in your library — stays
  # permissive on purpose: narrowing it makes files you already own
  # invisible to the whole app (roadmap item R1's own lesson).
  AUDIO_EXTENSIONS = {...}          # unchanged

  # What Seeker will FETCH from SoulSeek. Derived, not hand-picked:
  # exactly the formats metadata.py can actually write tags and cover
  # art to (ID3 -> mp3/wav/aiff/aif, FLAC, MP4 -> m4a). Downloading
  # anything else produces a file this app cannot finish processing.
  DOWNLOADABLE_EXTENSIONS = {".mp3", ".flac", ".wav", ".aiff", ".aif", ".m4a"}
  ```
  Add an assertion or a test that `DOWNLOADABLE_EXTENSIONS <=
  AUDIO_EXTENSIONS`, so the download set can never drift into something
  the scanner would refuse to index afterwards.
- [ ] **B5.2 — the judgement calls, stated rather than assumed.**
  - `.mp4` — the user asked for it, but an audio `.mp4` from SoulSeek is
    rare and a video `.mp4` is common; `.m4a` is the audio container
    Rekordbox and Serato actually expect, and mutagen's `MP4` class
    handles it. **Recommendation: `.m4a` in, `.mp4` out**, with a
    comment saying exactly this. Flag it for the user rather than
    burying it.
  - `.aac` (raw ADTS) — out. No reliable tag container, and there are
    zero in the real library.
  - `.aifc` — out, consistent with R1.3's existing reasoning.
  - `.ogg`/`.opus`/`.wma`/`.ape`/`.wv` — out.
  mutagen *could* tag Vorbis comments in `.ogg`, so "we can't tag it" is
  a scoping decision here, not a hard limit. Say so in the comment
  instead of implying it's impossible.
- [ ] **B5.3 — apply it at all three entry points, not just one.** This
  is the part a single-line change would miss:
  1. `quality._score_candidate` (`:52`) — the auto and needs-review
     tiers. Swap `AUDIO_EXTENSIONS` → `DOWNLOADABLE_EXTENSIONS`.
  2. `rank_candidates()` — used by the **Search page**
     (`main_window.py:1858`) and the CLI (`cli.py:549`) on **raw,
     unfiltered** search results. There is no extension gate on this
     path at all today, so a `.ogg` is listed and pickable.
  3. `download_manual(chosen=...)` — an explicit per-row pick
     **deliberately bypasses `select_downloads` entirely**
     (`download_service.py:~487`), so the gate must also exist as a
     final guard at request time.
  Put the guard in one shared predicate; three call sites, one
  implementation.
- [ ] **B5.4 — refuse loudly, never silently.** A user who explicitly
  clicks "Download this one" on a filtered-out format must get a real
  message ("Seeker only downloads mp3, flac, wav, aiff and m4a — this
  one is .ogg"), not a row that does nothing. Silent no-ops on an
  explicit click are the failure mode item 56 Phase 4.2 exists to
  prevent.
- [ ] **B5.5 — the `.ogg` already in the library.** Leave the file
  alone. It stays indexed and playable; only its tagging outcome is
  unsupported. **Ask the user** before doing anything with it — the
  standing rule covers it. Worth offering in the reply: a one-off
  re-download in FLAC via the Search page would resolve it cleanly.
- [ ] **B5.6** Tests: a `.ogg` candidate is excluded from
  `filter_candidates`, from `rank_candidates`' output, and from an

## B7 — Remove the `cover.jpg` sidecar feature

The user's three questions, answered, then a recommendation.

**How are the files named in a multi-album playlist folder?** Always
literally `cover.jpg`, never `cover1`/`cover2` — `_write_cover_jpg_sidecar`
(`metadata_service.py:42`) writes `file_path.parent / "cover.jpg"` and
returns `False` without touching anything if it already exists. So a
folder holding tracks from ten different albums gets **one** cover.jpg,
belonging to whichever track happened to be processed first, and the
other nine are silently not represented. The docstring is honest that
this assumes an album-shaped folder; the user's library is
playlist-shaped (`Neuro/`, `DnB/`, `Test/`, …), so in practice it writes
a wrong cover, not a missing one.

**Why didn't the files change in Finder?** Because `cover.jpg` is not a
macOS convention at all. It is read by Plex, Jellyfin, Kodi, foobar2000
and Traktor; Finder has never used a folder-level image for either the
folder icon or the files inside it. Nothing was going to change.

**Why did VLC and Apple Music show the art?** They read the **embedded**
art, which R4/item 75 already established is correct — VLC parses FLAC
picture blocks natively, and Music uses embedded artwork for local files.
That is confirmation the embedding works, not evidence that the sidecar
did anything.

So the feature costs new files written into the user's library and
returns nothing, in the one place it was meant to help. R4.3's rejection
of per-file custom Finder icons still stands (resource forks on an
exFAT-shaped external drive with `._` sidecars already present), so there
is no remaining route to Finder thumbnails for FLAC and WAV. **Remove
it.**

- [ ] **B7.1** Remove `_write_cover_jpg_sidecar` and both call sites
  (`metadata_service.py:535`, `:850`).
- [ ] **B7.2** Remove the Settings toggle (`settings_window.py:929`,
  `:949`) and the `write_cover_jpg_sidecars` config field
  (`config_store.py:45`, `:100`). **The loader must keep tolerating the
  key** in an existing config file — `load_config` reads via
  `data.get(...)`, so confirm an unknown/leftover key is ignored rather
  than raising, and test it against a real config JSON that still
  contains it. This is the same check-before-alter discipline schema
  changes get.
- [ ] **B7.3** Do **not** delete any `cover.jpg` already written into the
  library. Report to the user which folders have one (a read-only find),
  and let them decide. Standing rule.
- [ ] **B7.4** Record the reasoning in HISTORY as a deliberate reversal
  of R4.2 with the evidence above — not as a silent removal. R4.2 was a
  reasonable call on the information available then; it was tested in
  the real world and didn't pay off, and that is worth writing down.
- [ ] **B7.5** Remove or repoint the tests covering it, and say how many
  went.

## B8 — Spotify `401 Unauthorized`: the client is built once and never rebuilt

**CONFIRMED in source. Two bugs, one of which makes the other
unrecoverable without restarting the app.**

`Application.spotify` is a cached property (`application.py:338`):

```python
@property
def spotify(self) -> SpotifyClient:
    if self._spotify is None:
        token = self.auth_manager.get_valid_token()
        self._spotify = SpotifyClient(token.access_token)
    return self._spotify
```

`SpotifyClient.__init__` stores the **access token string**
(`client.py:77`) and `_get` sends it forever. `grep -n "_spotify\b"
application.py` finds only lines 142 (init), 339, 342, 346 — **nothing
ever resets it.** A Spotify access token lives one hour.

That is the whole failure the user saw: the first playlist loads worked
because the token was still alive; once the hour ran out every
subsequent call 401'd, on `/playlists/{id}/items` as in the screenshot,
because `_get` handles 429 and nothing else. Restarting the app from the
terminal "fixed" it because a fresh `Application` rebuilt `_spotify`,
which called `get_valid_token()`, which saw `expires_at` in the past and
refreshed. **It has nothing to do with which macOS user account was
running** — the same restart on the test account would have worked too.

The second bug is worse. `connect_spotify(force_reauthorize=True)` —
Settings' "Re-authorize" — clears the token file and resets
`_auth_manager`, then does:

```python
self.spotify      # application.py:236
```

But `_spotify` is **already non-None** in a session that has made any
Spotify call, so the property short-circuits and **the OAuth flow never
runs**. Re-authorize is a silent no-op, and the app keeps the dead token.
The one recovery the UI offers cannot work. `_sync_service` caches the
same stale client and is never reset either.

- [ ] **B8.1 — reset the cached client wherever the token changes.**
  `connect_spotify` must set `self._spotify = None` **and**
  `self._sync_service = None` (it holds the client) alongside
  `self._auth_manager = None`, before touching `self.spotify`. Audit
  every other place that changes auth state for the same omission.
- [ ] **B8.2 — the client must not hold a frozen token.** Give
  `SpotifyClient` a token **provider** (a `Callable[[], str]` bound to
  `auth_manager.get_valid_token`) instead of a string, so every request
  uses a token that `get_valid_token()` has already refreshed if needed.
  This is the real fix; B8.3 is the safety net beneath it.
- [ ] **B8.3 — handle 401 in `_get`, once.** On a 401: force a token
  refresh and retry the request **exactly once**; if the retry also

## B9 — The macOS menu bar icon (and what "Check now" does)

**The names first, since the user asked:** the strip along the top of
the screen is the **menu bar**; the icons on its right-hand side are
**menu bar extras** (Apple's API name is `NSStatusItem`, so "status
items" is also correct). **Control Center** is the one specific Apple
item with the two-slider glyph, not the whole area. Seeker's is a Qt
`QSystemTrayIcon`, which maps onto an `NSStatusItem`.

**Why it's a squircle. CONFIRMED, and the code already admits it**
(`main_window.py:5599`): `_build_tray_icon` loads
`packaging/icons/seeker_icon.icns` — the full-colour **app** icon — and
calls `icon.setIsMask(True)`. `setIsMask` makes macOS treat the image as
a *template*: colour is discarded and only the **alpha channel** is
stamped in the menu bar's current tint. The app icon's alpha is a solid
opaque rounded square, so the entire squircle becomes one filled blob.
The existing comment flags this as a known gap for "a future pass with
real asset tooling". This is that pass.

**A real template asset is already committed to the repo, untracked:**

```
packaging/icons/seeker_menubar_Template.png      37 × 18  RGBA
packaging/icons/seeker_menubar_Template@2x.png   75 × 36  RGBA
```

Derived from the real `seeker_icon.icns`, not redrawn: the 1024px icon
was thresholded on luminance (background is a flat 13.6, the artwork is
> 30, so the separation is clean), the faint background circle dropped,
the result cropped to the artwork's own bounding box, the two brow
strokes dilated slightly so they survive an 18px downscale, and the whole
thing emitted as black pixels with the glyph in the alpha channel — which
is exactly what a template image is. Checked at real size composited on
both a light and a dark menu bar: the eyes-and-brows mark reads clearly
in both. Filenames use macOS's `…Template` convention, and Qt picks up
the `@2x` file automatically via its high-DPI file convention.

- [ ] **B9.1** Point `_resolve_tray_icon_path()` at
  `seeker_menubar_Template.png` (both the dev-tree and the
  `sys._MEIPASS` branch) instead of `seeker_icon.icns`. Keep
  `setIsMask(True)` — with the right artwork it now does the right
  thing. Keep the `.icns` for the app/Dock icon, which is unaffected.
- [ ] **B9.2** Make sure `seeker.spec` bundles the new PNGs as `datas`
  — the existing comment on `_resolve_tray_icon_path` explains that
  anything not listed there leaves a **packaged build's** tray icon
  blank, which is exactly the failure mode to avoid repeating.
- [ ] **B9.3** Replace the "no image-editing tool available" comment
  with a short note on how the asset was derived (threshold, crop,
  brow dilation, alpha-only) so a future re-export is reproducible
  rather than re-guessed.
- [ ] **B9.4 — verify by looking at it.** Screenshot the real menu bar
  in both light and dark appearance and attach both. Do not close this
  on "the file loads" — item 75's lesson: it closes when the user says
  they can see the right picture.
- [ ] **B9.5 — "Check now" is misnamed.** It calls
  `self._trigger_backend_poll()` (`main_window.py:5226`), i.e. an
  immediate slskd download/upload status poll instead of waiting up to

  (`_on_check_for_updates_clicked`, `:2606`), a completely different
