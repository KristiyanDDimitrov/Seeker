   and P6.** P4 in particular has now been investigated three times

   first, maximized second.
4. Standing project rules still apply: no real user file modified
   without explicit confirmation; guarded idempotent migrations;

## P1 — Tagging button row squeezes the playlist panel

**Status: root cause CONFIRMED in source. No investigation needed —
build the fix.**

`main_window.py:2034 _build_tagging_controls()` returns a single
`QHBoxLayout` holding nine fixed-size children: 2 checkboxes, 2
`QLineEdit`s, and 5 push buttons ("Tag selected", "Tag playlist", "Fix
missing cover art", "Fill missing art URLs", "Rename files to match
metadata").

At `main_window.py:1417` that layout goes into `right`, and at
`:1379`/`:1430` the dashboard content is:

```
layout.addWidget(self.playlist_list, 1)   # QListWidget, tiny minimum
layout.addLayout(right, 3)                # contains the 9-widget row
```

A `QHBoxLayout`'s **minimum width is the sum of its children's minimum
widths** — stretch factors only distribute space *above* each item's
minimum, they never shrink an item below it. So `right` has a hard
floor of roughly 900–1000px, `playlist_list` has a floor of almost
nothing, and every pixel the window gives up is taken out of the
playlist panel. That is exactly the reported symptom, and it gets worse
with every button added — which is why it appeared when the Tagging
section grew.

### Fix

- [ ] **1.1 Add a real `FlowLayout`** (`src/seeker/ui/flow_layout.py`),
  the standard Qt flow-layout pattern: `hasHeightForWidth() -> True`,
  `heightForWidth(w)` laying items out row by row, and — the part that
  actually fixes this — **`minimumSize()` returning the widest single
  item, not the sum**. Use it for the tagging controls row.

  This solves both halves at once: the row reflows 1-row → 2-row → 3-row
  purely from available width (no resolution detection, no
  `resizeEvent` hooks, no breakpoint constants to tune), *and* the
  page stops imposing a 1000px floor on its parent. Prefer this over a
  `QGridLayout` + manual reflow — the grid needs a hand-tuned width
  breakpoint, which is a new untuned constant for something Qt can
  derive.

- [ ] **1.2 Give the playlist panel a real floor:**
  `self.playlist_list.setMinimumWidth(...)` sized to fit the longest
  realistic playlist name (measure with `QFontMetrics` against the
  theme font; flag the constant as untuned in a comment).

- [ ] **1.3 Consider replacing the raw `QHBoxLayout` at `:1372` with a
  `QSplitter`** (`setChildrenCollapsible(False)`, initial `setSizes`
  matching today's 1:3 ratio) so the user can also set the split
  themselves. Judgement call — do it only if it doesn't disturb the
  existing dashboard tests more than trivially.

- [ ] **1.4 Tests:** at 960×640 windowed, assert `playlist_list.width()`
  is at least its minimum and that the tagging row's
  `heightForWidth()` really does grow to 2+ rows; at 1600 wide, assert
  it collapses back to 1 row. Assert `dashboard_content.minimumSizeHint()
  .width()` is now well under 960.

## P2 — "Rename files" leaves numbered prefixes on files the preview said would lose them

**Status: NOT root-caused from source. Three real structural defects
found in the path; the specific failure needs Phase 0.2 to identify.**

What the source rules **out**: `build_track_filename()` builds the name
purely from Spotify artist/title, so a numbered prefix cannot survive a
successful rename by construction. `apply_renames` receives the same
`plans` list the dialog displayed (`main_window.py:2460`/`:2472`) — no
filtering between preview and apply. `match_all()` is never on a timer,
so a background re-match cannot silently demote a track mid-flow.
Reporting is honest — `failed` is counted, surfaced in the notice
(`help_text.py:286`) and every detail line goes to `tagging_results`.

So either those three files were **reported** as failures the user
didn't notice, or one of these three real defects hit:

### Defect A — the preview is not authoritative (CONFIRMED)

`RenamePreviewDialog` displays `plan.proposed_path.name`
(`main_window.py:855`). But `_apply_one_rename` **re-resolves the
target at write time** via `_resolve_collision()`
(`metadata_service.py:983`), which can legitimately return a different
name (`… (2).ext`). Nothing tells the user the written name differed
from the previewed one. "Preview said X, disk got Y" is precisely the
reported shape.

### Defect B — no within-batch target-collision check (CONFIRMED)

`plan_renames` plans every track independently against the filesystem
**as it is before any rename runs**. Two plans can target the same
final name (a track duplicated in the playlist, two remixes normalizing
to the same string, or an already-correct file whose name a later plan
also targets). At plan time neither is a collision, so both are shown
as clean renames with `collisions: 0`. At apply time the first one wins
the name and the second silently becomes `… (2).ext`.

### Defect C — a live download can land mid-preview (CONFIRMED)

`_open_rename_preview_dialog` calls `dialog.exec()` from the worker's
`on_finished` on the main thread. A modal `exec()` **keeps processing
timer events**, so `poll_timer` (2s) and `backend_poll_timer` keep
firing while the dialog is open — including `_trigger_backend_poll` →
`poll_downloads()`, which **moves completed SoulSeek files into the
library and writes `local_files` rows**. The user had downloads
retrying in this exact session (see P3). A file landing in the target
folder while the preview is open turns a planned clean rename into a
collision, or invalidates the plan's `local_file_id`.

### Fix

- [ ] **2.1** Do Phase 0.2 first and state which of A/B/C (or something
  else) actually produced the three files. Fix that one properly. Do
  not fix all three speculatively and declare victory.
- [ ] **2.2 (regardless)** `plan_renames` must detect **within-batch**
  target collisions: build the set of proposed final names across all
  plans and mark any duplicate target as `collision` at plan time, so
  the preview is honest about it.
- [ ] **2.3 (regardless)** When `_apply_one_rename`'s resolved
  `final_path.name != plan.proposed_path.name`, record a detail entry
  saying so explicitly (`"renamed to X, not the previewed Y"`) and
  count it in `collisions`. Silence here is what makes this class of
  bug invisible.
- [ ] **2.4 (regardless)** Block the poll timers for the duration of the
  rename preview dialog, or re-plan immediately before `apply_renames`
  and refuse (with a clear message) if the re-plan disagrees with what
  the user confirmed. Re-planning is the safer of the two — it also
  closes the "user left the dialog open for ten minutes" window.
- [ ] **2.5** The result panel is a `QPlainTextEdit` capped at 120px
  (`main_window.py:2105`) — every failure detail lands somewhere the
  user has to scroll a tiny box to find. Make the notice name the count
  of files whose written name differed from the preview, not just
  "N failed".
- [ ] **2.6** Regression test the real failing shape from 0.2 against a
  real filesystem, plus a within-batch-collision test (two tracks, one
  target name).

## P3 — "You're all set" reappears after being dismissed

**Status: root cause CONFIRMED in source. The retrying downloads are a
red herring — this happens unconditionally.**

`poll_timer` fires every 2s and is wired to `_poll_next_step`
(`main_window.py:966`). `_render_next_step` (`:3518`) calls
`self.next_step_notice.show_message(...)` **unconditionally** whenever
`_decide_next_step` returns a step, and `show_message` ends with
`self.show()` (`notice.py`). The user's X calls `dismiss()` → `hide()`.
Two seconds later the next tick re-shows it.

This also contradicts `InlineNotice`'s own docstring premise, which
says a notice "only ever clears when the user dismisses it" — the
next-step notice is poll-driven, so dismissal has no memory at all.

### Fix

- [ ] **3.1** Add a `dismissed = Signal()` to `InlineNotice`, emitted
  from `dismiss()`. (A signal, not reaching into `_dismiss_button` from
  `MainWindow` — other pages use this widget too.)
- [ ] **3.2** In `MainWindow`, keep `self._dismissed_next_step_key`.
  Build a key from the step's real identity — selected playlist id +
  `step.message` + `step.action`. On `dismissed`, store the current
  key. In `_render_next_step`, skip `show_message` when the new key
  equals the stored one; clear the stored key as soon as the key
  changes (so a *different* next step still surfaces, and "You're all
  set" reappears legitimately if the user later adds tracks).
- [ ] **3.3** Test: dismiss, run three poll ticks, assert still hidden;
  then change the underlying facts so the step differs, tick, assert it
  shows again.
- [ ] **3.4** Check whether `dashboard_notice` and the other
  `InlineNotice` instances have the same poll-driven resurrection
  problem. If any other notice is written from inside a polled render
  path, fix it the same way rather than leaving a second copy of this
  bug.

## P4 — Duplicates "Actions" column shows nothing (4th report)

**Status: a new, mechanical explanation that fits every prior
non-reproduction. Confirm with Phase 0.1 numbers, then fix.**

### Why three investigations missed it

They all asked "does `cellWidget(row, ACTIONS)` return a real widget?"
It does. That question cannot detect a widget that exists and is
clipped to near-zero visible width. Item 68 even reasoned that
`setStretchLastSection` "structurally prevents it from ever scrolling
off-screen" — true, and irrelevant: `setStretchLastSection` gives the
last column the **leftover** space, which can be almost none.

### The arithmetic

- The duplicates table has **8 columns** (`_DuplicatesColumn`,
  `main_window.py:183`).
- **No column width is ever set anywhere in this app.** `grep` for
  `setColumnWidth`, `setSectionResizeMode`, `resizeColumnsToContents`,
  `setDefaultSectionSize`, `setMinimumSectionSize` across `src/seeker/ui/`
  returns **nothing**. So columns 0–6 sit at Qt's default 100px each =
  **700px fixed**.
- `SIDEBAR_WIDTH = 200` (`:207`). Minimum window is **960×640**
  (`:945`). Viewport ≈ 960 − 200 − page margins − table border/scrollbar
  ≈ **~715px**. Actions therefore gets **~15px**.
- The Actions widget is "Keep all" radio + "Confirm delete" checkbox +
  "Delete" button (`_build_duplicate_group_actions`, `:3118`) — a
  `sizeHint().width()` in the **~280–300px** range.

At the tested default of 1180×760 it gets ~235px — still short, but
enough that a code-level introspection reads as "fine". Windowed, which
is how the user works, it collapses to a sliver. **P1 makes this
strictly worse**, since the tagging row's 1000px floor pushes the whole
window wider than the user wants it.

### Second, independent defect — stale spans (CONFIRMED)

`_render_duplicate_groups` calls `setSpan(...)` per group
(`:3113`) but **`clearSpans()` is never called anywhere in this file**
(verified by grep). `setRowCount()` does not clear spans. So a second
Find-duplicates run whose groups have different sizes inherits the
previous run's spans, and a stale span covering a new group's first row
will hide that group's Actions widget outright. Prior tests re-rendered
with the *same* group shapes, so the stale span was identical and
nothing broke.

### Fix

- [ ] **4.1** Call `self.duplicates_table.clearSpans()` at the top of
  `_render_duplicate_groups`, before `setRowCount`. Audit every other
  table in the app for the same omission.
- [ ] **4.2** Give the Actions column a real floor:
  `header.setSectionResizeMode(_DuplicatesColumn.ACTIONS,
  QHeaderView.ResizeMode.Fixed)` plus an explicit width taken from the
  actions widget's own `sizeHint().width()` — derived, not a magic
  number. Set sensible widths for the other columns too (PATH should
  stretch and hold the long value; Group/Format/Bitrate/Similarity/Keep
  should shrink to contents). Right now PATH is a 100px column holding a
  full relative path, which is its own usability problem.
- [ ] **4.3** Also set `header.setMinimumSectionSize(...)` and make the
  table scroll horizontally rather than crushing columns, so no future
  column can be silently squeezed to nothing.
- [ ] **4.4 The test that should have caught this.** At 960×640,
  windowed, with real duplicate groups: assert
  `header.sectionSize(ACTIONS) >= actions_widget.sizeHint().width()`
  **and** `actions_widget.visibleRegion().boundingRect().width() >=
  sizeHint().width()`. Add a second test doing two consecutive renders
  with **different group sizes** (e.g. a 3-file group then a 2-file
  group) and asserting the second render's Actions widgets are all
  visible — that is the stale-span regression test.
- [ ] **4.5** Delete or rewrite the existing "not reproducible"
  regression tests that only assert widget existence. Leaving them
  implies coverage that does not exist.

## P5 — Sharing: "slskd.yml has no active 'shares:/directories:' section to add to"

**Status: root cause identified with high confidence. Confirm with
Phase 0.3, then fix — plus two collateral defects found alongside it.**

### The cause

`add_location_to_share` resolves the config it edits from the **live
container's `/app` mount** (`sharing_service.py:350-361`), which is
`slskd_data_dir()` = `~/Library/Application Support/Seeker/slskd-data/`
(`docker_setup.py:104`).

That is **not** the `slskd-data/slskd.yml` in this repo. The repo copy
has a real, uncommented block at line 352:

```yaml
shares:
  directories:
    - /shared/music
```

…because it was hand-edited during roadmap item 13. The app-data copy
was never hand-edited: `bring_up_slskd` (`docker_setup.py:319`) passes
credentials as environment variables and **never writes an
`slskd.yml`** — slskd generates its own default there on first run, and
slskd's generated default has the entire `shares:` block **commented
out** (exactly like lines 43–53 of the repo copy).

`_insert_slskd_share_directory` (`sharing_service.py:573`) only accepts
a line that is exactly `shares:` at column 0 with an uncommented
`directories:` child. Against slskd's generated default that never
matches → the exact error the user saw. The check itself is correct;
the assumption that an active block already exists is not.

### Fix

- [ ] **5.1** `_insert_slskd_share_directory` must **create** the
  `shares: / directories:` block when no active one exists, rather than
  refusing. Append a real block at the end of the file (after a
  trailing newline), and keep the existing "insert into the existing
  block" path for when one is already there. Both paths need tests
  against **real** slskd-generated default text — commit a captured
  copy of a genuinely generated `slskd.yml` as a test fixture, not a
  hand-written approximation.
- [ ] **5.2 Collateral defect — partial write on failure (CONFIRMED).**
  The current order (`:379-390`) is: back up both files → **write
  docker-compose.yml** → parse slskd.yml → write slskd.yml. Any failure
  in the slskd.yml step leaves docker-compose.yml already mutated, and
  a retry adds the volume line a **second** time. Compute *both* new
  file contents first, then write both, and roll the compose file back
  from its backup if the second write fails.
- [ ] **5.3 Collateral defect — frozen-build compose path (CONFIRMED).**
  `compose_file_path()` (`docker_setup.py:80`) returns
  `sys._MEIPASS / "docker-compose.yml"` in a frozen build. `dist/` was
  rebuilt today (`Seeker.app`, `Seeker.dmg`, 20:47), so the user is
  very likely running the packaged app — in which case Sharing is
  editing and backing up a file **inside the app bundle**, which is
  wiped or replaced on the next build, and `is_self_managed()` compares
  the container's recorded config-file label against a bundle path that
  can change between launches. Decide and implement a real answer:
  copy `docker-compose.yml` into `slskd_data_dir()` on first run and
  treat *that* as the canonical, writable, stable compose file. Flag
  this explicitly — it affects every Sharing write, not just this bug.
- [ ] **5.4** Verify end to end against a **disposable throwaway
  container**, never the production one — the same discipline roadmap
  item 62 used.
- [ ] **5.5** Note only, no action needed: the repo's
  `slskd-data/slskd.yml` holds plaintext SoulSeek and web credentials,
  but `slskd-data/` **is** in `.gitignore` and `git ls-files slskd-data/`
  returns nothing — they were never committed. Verified; recorded here
  so nobody re-checks it.

## P6 — Cover art "still doesn't update" (4th report)

**Status: the write path is sound and was live-verified once. The
question this round is not "does it write" but "why does the user never
see it". Phase 0.4 decides between three very different answers.**

### What is already ruled out (do not re-investigate)

`embed_album_art` (`metadata.py:118`) is replace-not-append for all
three formats, sets `type=3` (front cover) and `desc="Cover"`, and
`_fix_one_track_art` calls `add_tags()` before reading/embedding and
`save()` after. `AlbumArtCache` is keyed by SHA-256 of the URL and
treats a corrupt entry as a miss. Phase 5.4 ran `seeker library fix-art
Test` for real and got `Fixed: 3, Already correct: 6`. **Bytes reach the
files.** Item 56 §0.4 already refuted the append hypothesis against
real files. Do not spend this round re-confirming any of that.

### The three live candidates, in priority order

**6a — The user is clicking the wrong button, and the app lets them.**
`_tag_one_track` sets `skip_tag_write = local_file.tagged_at is not None
and not force` (`metadata_service.py:344`) and returns early — **art is
never even considered for an already-tagged file.** For a library where
everything was tagged before the art fixes landed, "Tag playlist"
therefore updates zero pictures, every time, forever. The user gets
"skipped_already_tagged: N" and reasonably reads that as "nothing needed
doing". This fits "not a single picture has been updated" perfectly.

**6b — The art is on disk and the user's software can't read it.** Two
real sub-cases:
  - **ID3 version.** `mutagen_file.save()` defaults to writing
    **ID3v2.4**. Rekordbox, Serato, Traktor and macOS's own metadata
    importer are all markedly more reliable with **v2.3**. This is a
    one-argument change (`save(v2_version=3)`) with a real chance of
    being the whole answer for MP3/WAV.
  - **WAV.** `_WaveID3` is a real `ID3` subclass so mutagen writes an
    APIC into the RIFF container and reads it back byte-exact — but
    that only proves *mutagen* can read it. Essentially nothing else in
    a DJ's toolchain reads embedded art from WAV. If the library is
    WAV-heavy this is unfixable by tagging and must be **stated
    honestly in the UI**, not silently counted as a success.

**6c — `album_art_url` is NULL.** Already handled (`no_url` outcome +
"Fill missing art URLs" button), but confirm it is not the bulk case.

### Fix

- [ ] **6.1** Report Phase 0.4's numbers first: per-format counts, how
  many files have correct embedded art *right now*, and the ID3 version
  actually on disk. That single measurement decides 6a vs 6b vs 6c.
- [ ] **6.2 (6a, do regardless)** Decouple the art step from
  `tagged_at`. Either always evaluate art in `_tag_one_track` even when
  the text-tag write is skipped, or — cleaner and closer to the
  existing design — when a tag run skips N tracks as already tagged,
  the notice must say plainly that **their cover art was not checked**
  and offer "Fix missing cover art" as the next action. Right now the
  user has no way to learn that from the UI.
- [ ] **6.3 (6b)** If 0.4 shows v2.4 on disk, write ID3 as
  **v2.3** (`save(v2_version=3)`) for MP3 and WAV. Verify by reopening
  the real file and by checking whether art now appears in the user's
  actual DJ software — **ask the user to confirm visually; mutagen
  reading its own write proves nothing here.** This is the one check
  that has never been done in four rounds.
- [ ] **6.4 (6b)** If the library is materially WAV, add an explicit
  outcome (`art_written_but_format_rarely_supported` or similar) and
  surface it. A count of "written" that the user can never see is
  dishonest reporting of exactly the kind Phase 4.2 was built to end.
- [ ] **6.5** Do **not** close this item on "the bytes are in the file".
  It closes when the user says they can see a picture.

One commit per P-item, each independently verified, in this order:
P3 (smallest, fully understood) → P1 → P4 → P5 → P6 → P2 (needs the
most live investigation). `mypy --strict src/` clean and the full suite
green before each commit. Update `docs/TASKS.md`, `docs/HISTORY.md` and
`CLAUDE.md` as the project's conventions require — and in HISTORY, say
plainly for P4 and P6 that the previous rounds' conclusions were wrong
and why, rather than adding a fourth entry that reads like the first
three.
