### 254 — The lock test: a wheel for every shipped platform (round 13 S2b)

**Problem.** `required-environments` makes `uv lock` fail only for a
package with no sdist. numba, llvmlite and numpy ship sdists, so
nothing stopped a relock from moving Intel off its wheels (§253, H2).
A row-worker wrote `tests/test_lock_platforms.py`, now the only guard.

**How it reads the lock.** It loads `uv.lock` with `tomllib` and walks
the graph from the editable project, every dependency group included,
once per shipped platform: darwin/arm64, darwin/x86_64, win32/AMD64,
each a full PEP 508 marker environment at the `.python-version`
Python, so nothing comes from the host. An edge whose `marker` is
false is not followed; an `extra` brings in the target's
`optional-dependencies` (optype[numpy]). A forked package's entry is
the one whose `resolution-markers` match, and the walk asserts exactly
one does. Every package reached needs a wheel `packaging.tags` accepts
(`cpython_tags` + `compatible_tags`; `mac_platforms((26, 0), arch)`):
cp313, abi3 or pure Python; universal2 counts, cp313t and cp314 don't.
No wheel at all fails as "builds from source". A failure names the
package, version and platform. Which macOS a wheel needs is not
checked here; that is the bundle's `minos` check (S6).

**Guards against a blindfold.** The three platforms map one-to-one
onto the lock's `required-markers`, each in exactly one top-level
`resolution-markers` fork. Together the walks reach every locked
registry package (72 of 72); pyobjc-framework-cocoa is reached on
darwin and not on win32; Intel takes a different numba, llvmlite and
numpy from arm64. Per platform 65 / 65 / 64 packages, S2's `uv export`
counts.

**Measured.** Deleting numba 0.62.1's one x86_64 wheel from a scratch
copy fails it with `numba 0.62.1 ships no wheel: it builds from source
on darwin/x86_64`; the real lock passes. Removing the constraints and
running a plain `uv lock` changes nothing: uv keeps locked versions.
Relocking with `-P` for the four forked packages moves every platform
to numba 0.68.1 and llvmlite 0.50.0, and the test names both for
darwin/x86_64 (numpy 2.5.4 still ships an Intel wheel). So the risk
bites on an upgrade (Dependabot, `uv lock --upgrade`), not a plain
relock. Two permanent cases cover it: one deletes the Intel numba
wheel, one gives Intel the native numba's wheels. 16 tests, ~1.3 s.
A Linux-only dependency, if ever locked, fails the reach-every-package
test deliberately: add Linux as a platform or exclude it with a
reason. `pyproject.toml`'s `required-environments` comment points at
the test.

### 265 — A wait on the process-wide worker count (round 13 S4c)

`check-intel` run `41550884285` (`826608b`) failed
`tests/pages/test_sharing_page.py::test_quit_stops_the_wait_for_a_new_share`
with `waitUntil timed out in 2000 milliseconds`, at the test's last
line: a wait for `len(workers._callbacks)` to equal a count taken before
the click.

**What is established.** That predicate compares two numbers that mean
different things. `_callbacks` is every in-flight task of the process,
so any unrelated worker moves it, and the add flow's finish handler
(`_on_add_location_to_share_finished`) ends in `_refresh_sharing()`: the
flow is two workers, the second started after the test's `waitForDone`
had returned. The test's own comment said the flow ends when "the
worker's finished handler has run"; the real end is that refresh's
handler. Locally, in six runs, the baseline was 0 and nothing else was in
flight; after `waitForDone` the registry held 1 (the add's handler not
yet delivered) and `fakes.settle_workers` took it to 0 with the success
notice shown.

**What is not.** Why the wait timed out on the runner. Two mechanisms fit
and neither was observed: the count skipped the baseline between two
polls (or an unrelated worker held it off), or the runner stalled for
more than 2 s. UNVERIFIED. `pytest -q` on that job records no durations,
so the logs cannot say which.

**Fix** (tests only). The test ends on `settle_workers(window)`, the
window's own pool, and the baseline is gone. `tests/test_wait_sweeps.py`
fails any `waitUntil` whose condition reads `_callbacks` (one offender on
`HEAD`: this test; `test_stress_e2e.py`'s `_pump` drains to an absolute 0
and is not a `waitUntil`). `check-intel` now runs `pytest --durations=25
--durations-min=1.0` (`test_ci_workflow.py` pins it), so the next run
shows whether the runner stalls.

**Not done: the sweep of short waits.** An AST count (an earlier `grep`
undercounted) finds 422 `waitUntil` calls: 346 at `timeout=2000`, 9 at
1000, 1 at 500, 1 at 4000, 65 on the 5 s default; 70 of the short ones
are in `test_dashboard_page.py`. They are one idiom, a widget state after
a worker's handler, which is the right thing to wait on (`tests/
CLAUDE.md`); none is a baseline comparison, and none was audited one by
one. Whether to give them one longer, named bound is open, and the data
should come first: a `waitUntil` returns as soon as its condition holds,
so a longer bound costs a green run nothing, but without a stall on
record it is a guess at the cause.

Main with S4c: `2574 passed, 1 skipped` (Cocoa), mypy clean on 149 files,
ruff 0. Not provable locally; only Intel runs confirm it.
