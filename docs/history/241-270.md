### 254 — The lock test: a wheel for every shipped platform (round 13 S2b)

**Problem.** `required-environments` makes `uv lock` fail only for a
package with no sdist. numba, llvmlite and numpy ship sdists, so
nothing stopped a relock from moving Intel off its wheels (§253, H2).
A row-worker wrote `tests/test_lock_platforms.py`, now the only guard.

**How it reads the lock.** It loads `uv.lock` with `tomllib` and walks
the graph from the editable project, every dependency group included,
once per shipped platform: darwin/arm64, darwin/x86_64, win32/AMD64,
each a full PEP 508 marker environment at the `.python-version`
Python, so nothing comes from the host. An edge whose `marker` is
false is not followed; an `extra` brings in the target's
`optional-dependencies` (optype[numpy]). A forked package's entry is
the one whose `resolution-markers` match, and the walk asserts exactly
one does. Every package reached needs a wheel `packaging.tags` accepts
(`cpython_tags` + `compatible_tags`; `mac_platforms((26, 0), arch)`):
cp313, abi3 or pure Python; universal2 counts, cp313t and cp314 don't.
No wheel at all fails as "builds from source". A failure names the
package, version and platform. Which macOS a wheel needs is not
checked here; that is the bundle's `minos` check (S6).

**Guards against a blindfold.** The three platforms map one-to-one
onto the lock's `required-markers`, each in exactly one top-level
`resolution-markers` fork. Together the walks reach every locked
registry package (72 of 72); pyobjc-framework-cocoa is reached on
darwin and not on win32; Intel takes a different numba, llvmlite and
numpy from arm64. Per platform 65 / 65 / 64 packages, S2's `uv export`
counts.

**Measured.** Deleting numba 0.62.1's one x86_64 wheel from a scratch
copy fails it with `numba 0.62.1 ships no wheel: it builds from source
on darwin/x86_64`; the real lock passes. Removing the constraints and
running a plain `uv lock` changes nothing: uv keeps locked versions.
Relocking with `-P` for the four forked packages moves every platform
to numba 0.68.1 and llvmlite 0.50.0, and the test names both for
darwin/x86_64 (numpy 2.5.4 still ships an Intel wheel). So the risk
bites on an upgrade (Dependabot, `uv lock --upgrade`), not a plain
relock. Two permanent cases cover it: one deletes the Intel numba
wheel, one gives Intel the native numba's wheels. 16 tests, ~1.3 s.
A Linux-only dependency, if ever locked, fails the reach-every-package
test deliberately: add Linux as a platform or exclude it with a
reason. `pyproject.toml`'s `required-environments` comment points at
the test.
