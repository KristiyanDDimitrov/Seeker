### 213 — Round 12, before S16: the Library flake, and tests that reached the real docker

**Why.** Kris asked that nothing be left hanging before release
engineering. The S15 handoff carried two blockers: the Library flake
(`test_library_track_list_refreshes_after_a_tag_run` timed out on CI
in `37932732255`, the first attempt of `37977966814`, a commit that
touched no `ui/` code, and both attempts of `37994812022`; never
locally, offscreen included), and a test run that had recreated
Kris's slskd container (§208 → "Observed"). Not a row of the plan;
recorded here as the pre-S16 clean-up.

**The flake: the recorded lead was wrong.** The lead (§201, §207) was
an older load for the same playlist landing last. It could not cause
this test's timeout: the fake's `get_playlist_track_status` returns
the very list the test mutates in place, so any load rendering after
the mutation shows the change. The real cause: a finished tag run
never reloaded Library's track list. `TaggingPanel._render_tag_result`
rendered the result and notice but never called
`host.refresh_track_table()` (Fix missing cover art and Rename did).
The test passed only because `_window_on_library` starts two loads
(the shared selection's deferred reconcile, then the page switch):
when the second rendered after the test's mutation, the list showed
"Tagged" with no help from the tag run. When both landed before
`waitUntil(rowCount == 4)` returned, nothing reloaded and it timed
out, which a slower runner makes likelier. In the app: Library's Tags
and Cover art lamps stayed stale after Tag playlist, Tag selected or a
row's Tag until the page was shown again.

**What changed.**
- `8d51517`: `_render_tag_result` asks the host to reload. The test
  now drains the initial loads (`thread_pool.waitForDone`, then
  `processEvents`) before the mutation; on HEAD it failed 3 of 3 with
  the `waitUntil` timeout, and passes 3 of 3 with the fix.
- `caaf9ca`: the old lead, fixed anyway, since it is real: a load for
  the same playlist that started earlier and finished later repainted
  statuses read before a run changed the files. Each load carries a
  counter (`_tracks_load`) and a superseded one is dropped, whichever
  playlist it was for. The new test holds the older load on an event
  until the newer one has rendered; on HEAD the release repaints "Not
  tagged".
- `314a14f`: no test runs the real `docker`. `conftest.py` replaces
  `subprocess.Popen` for the whole session with a subclass that
  refuses any argv whose executable is named `docker`, raising a
  `FileNotFoundError` subclass (every caller already treats a missing
  executable as "Docker not installed", so the run stays
  deterministic), and an autouse fixture fails the test during which
  the attempt was made. Session scope, so a worker outliving its test
  is refused too and fails whichever test is running.
  `test_the_suite_refuses_to_run_the_real_docker` pins it. A test
  that fakes `subprocess.run` never reaches `Popen`, so
  `test_docker_setup.py`'s fakes are unaffected.

**The docker incident.** `docker inspect` (§208) showed the container
created 2026-10-07 13:03:21 UTC (16:03:21 local), between S33's
`8e52af0` (16:02:37) and `75f3cdb` (16:04:40), "the SoulSeek step's
outcomes go on a notice", with `/app` bound under
`test_wizard_content_is_one_cen0/platformdirs-data/` and
`/shared/music` bound to `test_bring_up_soulseek_real_co0`. The share
path from one test and the data directory from another fit a worker
from the bring-up test outliving it: its `bring_up_slskd` monkeypatch
undone, it ran the real one while the later test's `platformdirs`
patch was in force (inferred, UNVERIFIED; the test was being edited
and its state then is not in git). With the guard in place the
current suite reaches `docker` nowhere: the full run under it was
`2238 passed, 1 skipped`, before the new tests. A probe calling
`detect_docker_state()` was refused and failed at teardown, as
designed. **Observed today:** `docker ps -a` lists no containers at
all; Kris's slskd container no longer exists (removed outside Seeker:
no Seeker code runs `docker compose down` or `docker rm`). Seeker
needs a bring-up from Settings → Connections (or the wizard) before
the next real download.

**Decisions.**
- A test fixed for a flake fails on HEAD deterministically first: it
  drains what it does not test rather than relying on timing.
- Refuse at `Popen`, not `bring_up_slskd`: every spawn path is
  covered, read-only probes (`docker info`) included, since a test's
  outcome must not depend on whether the machine runs Docker.
