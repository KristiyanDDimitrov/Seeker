### 151 — Round 11 S12 part 1 (§12.1, §12.2, §12.4): the poll says slskd is down; a Start slskd that never guesses

**Findings:** A-11 (an unreachable slskd was invisible). §12.3 (the UI
notices and tray edge-triggering) and §12.5 (A-58, first-session
download notifications) are not done; S12 stopped at its named split
point, after §12.2.

**What was wrong.** `DownloadService.poll_downloads` wrapped each
request in `except Exception`. With slskd refusing connections, every
`get_download_status` raised `httpx.ConnectError`, each one was counted
in `counts["failed"]`, and the poll returned normally: nothing told
anyone that slskd was down. Two further effects found reading the code:

- A due `locked` row's retry went through `_retry_locked_request`,
  whose `except Exception` branches call `_advance_locked_retry`
  before re-raising. So every 20 s poll during an outage spent one of
  the row's `LOCKED_RETRY_MAX_ATTEMPTS` (8) attempts against a peer it
  never reached. An outage longer than the backoff sum could turn a
  merely locked file `unavailable`.
- `seeker downloads status` got no error at all, only inflated
  `Failed:` counts.

**Failing tests first** (`tests/test_download_service.py`, a fake
client raising `httpx.ConnectError` from `get_download_status` and
`request_download`), on `HEAD` `2bacbde` plus only the new exception
class:

```
E       Failed: DID NOT RAISE SlskdUnreachableError
E       Failed: DID NOT RAISE SlskdUnreachableError
2 failed, 111 deselected
```

**Fix (`ab23d51`).** `soulseek/client.py` gains
`SlskdUnreachableError(base_url)`. Its message is the one sentence the
UI and CLI show: "SoulSeek isn't reachable — downloads are paused until
slskd is running." `poll_downloads` catches `httpx.TransportError` in
both per-request loops, ahead of `except Exception`, and raises it:
the first refusal aborts the poll, so no request is counted and no row
changes. `_retry_locked_request` re-raises a transport error *before*
`_advance_locked_retry`, so the retry budget is spent only on attempts
that reached slskd. Tests after: `113 passed`. A transport error covers
timeouts too (`httpx.TimeoutException` subclasses it); slskd hanging is
reported the same way as slskd refusing.

**CLI (§12.4, `95a344a`).** `cli.run` adds `SlskdUnreachableError` to
its caught errors. Before: a traceback. After: exactly the sentence on
stdout and exit status 1. The test asserts the whole of stdout, so a
"Details:" line or any other extra would fail it.

**Start slskd (§12.2, `fa4a1e7`).** `Application.restart_slskd()`
calls `start_slskd(..., persist=True)`, the one bring-up method (§140),
with the stopped container's live `/shared/music` mount and the saved
SoulSeek login. No fourth orchestration copy. It raises
`docker_setup.SlskdStartRefusedError`, with a sentence saying what to
do, instead of guessing:

- Docker not installed, or not running ("Open Docker Desktop, then try
  again");
- the container is not self-managed (`SharingService.is_self_managed`),
  or its share cannot be read. Both cover "the container is gone", and
  the refusal points at Settings → Connection, whose flow asks which
  location to share;
- no saved SoulSeek login.

Six tests, which failed first because the method did not exist. The
Compose template has `restart: unless-stopped`, so after a reboot the
container normally returns by itself once Docker Desktop is up. The
button matters for a container that was stopped by hand.

**Numbers at close-out:** pytest `1506 passed, 1 skipped, 6 warnings`;
`mypy --strict src/` clean (113 files); `ruff check src tests` 0
findings.

### 152 — Round 11 S12 part 2 (§12.3, §12.5): the outage on screen; first-session download notifications

**First-session notifications (§12.5, `1b86ebc`).**
`TrayController.seed_notification_cutoff` set the cutoff only when
history held an event, and `check_for_download_notifications` returns
while it is `None`. With empty history at startup it stayed `None` for
the whole session, so a fresh install never saw a "downloads finished"
notification. Failing test first:
`test_download_notifications_fire_after_seeding_found_no_history`
(empty history, then a new DOWNLOADED event, then a check) timed out
waiting for the cutoff on unmodified HEAD. Fix: an empty seed sets the
cutoff to `datetime.now(UTC).isoformat()`, the format
`download_request_repository` writes `completed_at` in, so the string
comparison orders correctly. `None` now means only "seed in flight".

**The outage on screen (§12.3, `c9014cf`).** New
`ui/slskd_status.py`:

- `SlskdStatus`, a QObject on `PageContext.slskd_status` (the
  `PlaylistSelection` shape). Only `MainWindow._trigger_backend_poll`
  writes it. `mark_unreachable`/`mark_reachable` return True, and emit
  `changed`, on an edge only.
- The poll's worker closure catches `SlskdUnreachableError` and
  *returns* it, because `run_worker`'s `on_error` receives only text.
  `on_finished` marks the state; on the up-to-down edge it calls the
  new `TrayController.notify_outage`, which honours "notify errors" but
  has no cooldown, since the edge already bounds it to once per outage.
  A recovery re-arms it silently. `on_poll_error` keeps other poll
  errors, now with `describe_error`'s text instead of the fixed
  "couldn't reach slskd" sentence.
- Dashboard: `_NextStepFacts.slskd_unreachable_message`, checked first
  in `_decide_next_step` (kind `warning`, action `start_slskd`).
  `changed` is connected to `_poll_next_step`, so the notice appears
  and clears at once rather than on the next 2 s tick.
- Downloads: a persistent `outage_notice` driven by `changed`, plus its
  own `notice`/`status_label` `FeedbackTarget` for Start slskd's
  outcome.
- `start_slskd(context, button, feedback)` runs
  `Application.restart_slskd` as busy action `start_slskd` (activity
  strip "Starting slskd…"), with the notice's own action button
  (`InlineNotice.action_button`, now public). Success reads "slskd is
  starting. Downloads resume as soon as it answers."; it does not
  clear the outage itself, because the container answers a few seconds
  after Compose returns. The next good poll clears it.

Eight tests in `tests/pages/test_slskd_outage.py` plus one in
`test_next_step.py`: edge semantics, both pages' notices, once per
outage and again after a recovery, clearing on the first good poll, a
non-outage error staying out of the outage state, the settings switch,
and Start slskd from each page (success on Dashboard, a refusal on
Downloads, which leaves Dashboard's notice untouched). On HEAD the
module did not exist (`ModuleNotFoundError`), and
`_NextStepFacts(slskd_unreachable_message=…)` raised `TypeError`.

**A known cosmetic edge.** `BusyActionRegistry.end` restores the
button's text as it was at `begin`. If the Dashboard's next step
changes while Start slskd is still running, the shared notice button
reads "Start slskd" for up to one 2 s tick, until `_render_next_step`
sets it again. Not worth a second mechanism.
