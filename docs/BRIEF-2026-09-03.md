## P7 — Duplicates "Actions" column, 5th report. **My previous root cause was wrong.**

**Correct the record before writing code.** Item 73's fix was built on
the previous brief's claim that the Actions column was clipped to
near-zero width because no column widths were ever set. The user's new
screenshot **refutes that**: the Actions column is roughly **800px
wide**, the header is centred in it, the Keep column's radio buttons
render fine two columns to the left — and the Actions cells are still
completely empty. Width was never the problem.

Item 73's column sizing and `clearSpans()` are both still worth having
(the sizing is genuinely good, and `clearSpans()` fixed a real second
defect plus a third in `_render_sharing_uploads_table`). They just
didn't fix *this*.

### The new hypothesis — the blank spacer widget covers the real one

`_render_duplicate_groups` still does this, in this order:

```python
self.duplicates_table.setCellWidget(group_first_row, ACTIONS, <real widget>)
for other_row in range(group_first_row + 1, row):
    self.duplicates_table.setCellWidget(other_row, ACTIONS, QWidget())   # blank
self.duplicates_table.setSpan(group_first_row, ACTIONS, len(group.files), 1)
```

`QTableView::visualRect(index)` resolves a spanned region through
`QTableViewPrivate::spanAt()` / `visualSpanRect()`, which returns the
**whole span's rectangle for every cell inside the span**, not just its
top-left cell. If that is so, then each blank `QWidget()` on the
covered rows is given geometry equal to the entire span rect, sits
directly on top of the real actions widget, and — being added to the
viewport later — paints over it.

That single mechanism explains every observation at once, including the
four failed reproductions:

- `cellWidget(first_row, ACTIONS)` returns a real widget → every prior
  existence-based test passes.
- The widget's own `visibleRegion()` may even be non-empty (it is not
  hidden, just occluded by a sibling) → item 73's *new* geometry test
  can pass too, which is why it also failed to catch this.
- Column width is irrelevant → matches the wide-and-still-empty
  screenshot.
- The cells look like empty table cells, because that is literally what
  is painted on top: a bare unstyled `QWidget`.

### The experiment — run this first, it settles it in 30 seconds

- [ ] **7.1** Save and run this on the Mac (`uv run python repro.py`):

```python
from PySide6.QtWidgets import (QApplication, QTableWidget, QWidget,
                               QHBoxLayout, QPushButton)
app = QApplication([])
t = QTableWidget(4, 2)
real = QWidget(); QHBoxLayout(real).addWidget(QPushButton("DELETE"))
t.setCellWidget(0, 1, real)
blank = QWidget()
t.setCellWidget(1, 1, blank)
t.setSpan(0, 1, 2, 1)
t.resize(800, 300); t.show(); app.processEvents()
print("real  geom:", real.geometry(), "visible:", real.isVisible())
print("blank geom:", blank.geometry(), "visible:", blank.isVisible())
print("child order:", [c is real and "REAL" or c is blank and "BLANK"
                       for c in t.viewport().children()
                       if c in (real, blank)])
print("real visibleRegion:", real.visibleRegion().boundingRect())
```

If `blank.geometry()` covers `real.geometry()` and blank comes later in
child order, the hypothesis is confirmed. **Report the real output
either way** — if it is refuted, say so plainly and go to 7.4.

- [ ] **7.2 (the fix, if confirmed)** Stop placing widgets on
  span-covered cells at all. Delete the `for other_row … QWidget()`
  loop — a spanned region needs nothing in its covered cells, and the
  "blank cell, not a misleading control" intent the comment cites is
  satisfied by the span itself. If something must be cleared there,
  call `removeCellWidget(other_row, ACTIONS)` instead. Also call
  `setSpan` **before** `setCellWidget` for the group's first row, so the
  widget's geometry is computed against the final span rect.
- [ ] **7.3** Audit every other `setSpan` + `setCellWidget` pair in the
  codebase for the same ordering (item 73 already found the sharing
  uploads table; check the track table's empty-state span at
  `main_window.py:1775` and any others).
- [ ] **7.4 (if 7.1 refutes it)** Do not guess again. Take a real
  screenshot of the running app from inside the test
  (`widget.grab().save(...)`) and compare pixels in the Actions cell
  against a control cell. Four rounds of introspection-based
  investigation have now failed; the next check must be pixels.
- [ ] **7.5** The regression test must be occlusion-aware, not just
  geometry-aware: assert that `t.viewport().childAt(centre_of_actions_
  cell)` is the real actions widget (or one of its children), not some
  other widget. That is the property all four rounds missed.

## P8 — Duplicates: "0 files in scope", fingerprinting finds nothing

The screenshots show `216 files in scope` on one account and `0 files in
scope` / `Fingerprinted: 0, Skipped: 0, Failed: 0` on the other, for
folders under the same `/Volumes/X9 Pro/Music/`. Two candidate causes,
and they are not mutually exclusive.

### 8a — Most likely: a different database, not a regression

Per 0.2, the two accounts have separate `seeker.db` files. If this
account's `Music` location has never been scanned (or the files were
scanned into a *different* registered location), `_files_for_scopes`
returns `[]` and every count is legitimately 0. That also explains
"tried the full folder, still didn't work" — a whole-location run
against an unscanned location is also 0.

- [ ] **8.1** Settle it with one query before changing any code:

```sql
SELECT l.id, l.name, l.path, COUNT(f.id) AS files,
       SUM(f.fingerprint IS NOT NULL) AS fingerprinted
FROM library_locations l
LEFT JOIN local_files f ON f.location_id = l.id
GROUP BY l.id ORDER BY l.id;
```
  (adjust the fingerprint column name to the real schema). Report the
  real rows. If `Music` has 0 files, the answer is "this account was
  never scanned" — say so, and see 8.4.

### 8b — A real design bug regardless: the wrong location can win

`DuplicateService.resolve_folder_scopes` (`duplicate_service.py:302`)
matches each folder against **every** registered location and takes the
**first** one it is relative to, in `get_all()` order — it never
considers which location the user actually selected, and it does not
prefer the most specific match. With both `x9-pro` (`/Volumes/X9 Pro`)
and `Music` (`/Volumes/X9 Pro/Music`) registered, a folder of
`/Volumes/X9 Pro/Music/House` can resolve to `x9-pro`, and then
`get_all_for_location(x9_pro.id)` returns whatever *that* location has
scanned — plausibly nothing.

- [ ] **8.2** Make the match **most-specific-wins**: score every
  candidate location by the length of its resolved path and keep the
  longest that the folder is relative to. Add a test with two nested
  registered locations asserting the inner one is chosen.
- [ ] **8.3** Report the resolution honestly in the UI: the scope count
  line should say which location(s) the folders resolved to, e.g.
  `216 files in scope (Music).` A silent 0 with no explanation is what
  made this unreadable.
- [ ] **8.4** When a scope resolves to a location with zero *scanned*
  files, say that specifically — "this location has no scanned files;
  run Rescan and match library first" — instead of a bare
  `0 files in scope.`

## P10 — Square-edged widgets break the rounded card corners (global)

Visible in the Sharing table screenshot: the table has
`border-radius: RADIUS_CARD` from `theme.py`, but the full-width
`QPushButton` cell widgets in the Action column have square corners and
sit flush against the table's edge, cutting the rounded corners off. The
user reports it across most tabs.

**The mechanism, and why a CSS-only fix cannot work:** Qt's
`border-radius` on a widget does **not** clip that widget's children.
Any `setCellWidget` widget that reaches the table's edge will always
paint over the rounded corner. So the fix has to be structural, not a
stylesheet tweak.

- [ ] **10.1** Add `theme.make_card(inner: QWidget) -> QFrame`: a
  `QFrame` that owns the rounded border, background and radius, with a
  small uniform content margin, containing an `inner` styled
  `border: none; background: transparent`. Route every `QTableWidget`
  and `QListWidget` in the app through it. The inner widget then never
  touches the rounded edge, whatever it contains.
- [ ] **10.2** Add `theme.cell_widget(*widgets) -> QWidget`: the single
  place cell-widget containers are built, applying consistent
  `setContentsMargins(SPACING_SM, SPACING_XS, SPACING_SM, SPACING_XS)`
  and `setSpacing(SPACING_SM)`. Replace every hand-rolled
  `QWidget()` + `QHBoxLayout` + `setContentsMargins(0,0,0,0)` at a
  `setCellWidget` call site with it — `_build_duplicate_group_actions`
  is one; grep for the rest. This also fixes the buttons visually
  jamming into each other and into the gridlines.
- [ ] **10.3** Give in-cell buttons a modest `setMaximumWidth` or stop
  stretching them to the full column, so an action button reads as a
  button rather than as a filled cell (see the "Add to my SoulSeek
  share" cells).
- [ ] **10.4** Verify with a real screenshot per page
  (`window.grab().save(...)`), not by reading the stylesheet. Attach the
  before/after for at least Sharing, Duplicates, Downloads and Review.

## P12 — "Rescan _match library" — a Qt mnemonic, not a typo

`main_window.py:1351` is `QPushButton("Rescan & match library")`. Qt
treats `&` in button text as a keyboard-mnemonic marker: it is consumed
and renders as an underline under the following character, giving
"Rescan _match library".

- [ ] **12.1** Change it to `"Rescan and match library"` (simplest, and

## P13 — New feature: manual track search and download

**The ask:** search for and download a track that isn't in any Spotify
playlist, reusing the existing "take the best quality available, fall
back to lower until something actually downloads" behaviour, so the user
doesn't have to open the SoulSeek client itself.

**The good news:** that behaviour already exists and needs no new
ranking logic. `quality.select_downloads()` (`quality.py:183`) already
returns `(settled, upgrade_shortlist, needs_review)` — best practical
unlocked candidate, with everything better kept as an upgrade
shortlist — and `poll_downloads()` already runs the retry/backoff/
upgrade cycle over it. `_score_candidate` uses only artist + title, no
duration, so a manually-entered track scores exactly like a Spotify one.

### Design

- [ ] **13.1 — Model.** A manual track is a **real `tracks` row that
  belongs to no playlist**, with id `manual:<uuid4>`, `album=""`,
  `duration_ms=0`. Verified: `download_requests.track_id` is a plain
  `TEXT NOT NULL` with **no** foreign key to `tracks`
  (`schema.py:80-86`) — only `playlist_tracks` has that FK — so
  everything downstream (Downloads page, History, `poll_downloads`,
  move-into-place) works unchanged. No schema change, no migration.
  **Do verify** that the post-download match/move step doesn't depend on
  a non-zero `duration_ms`; if it does, record the real duration from
  the completed file instead of forcing 0.
- [ ] **13.2 — Destination.** `_resolve_destination(playlist)`
  (`download_service.py:1284`) takes a `Playlist`. Refactor it to accept
  `playlist: Playlist | None` and, for `None`, resolve the configured
  default destination directly with a fixed `"Manual"` subfolder (never
  the per-playlist subfolder rule, which has no meaning here). Same
  "return None means the caller must prompt" contract as today, so the
  existing set-a-destination dialog is reused, not duplicated.
- [ ] **13.3 — Service.** `DownloadService.search_manual(artist, title)
  -> list[SoulseekFile]` (a real `soulseek.search()` with the same
  comma-stripped query construction `download_playlist` uses) and
  `DownloadService.download_manual(artist, title, chosen: SoulseekFile
  | None = None) -> dict`. With `chosen=None` it runs the exact same
  `select_downloads` path as a playlist download — best-first with
  fallback — and persists the settled row plus the upgrade shortlist.
  With `chosen` set, it honours an explicit user pick (see 13.5). Never
  duplicate the search or ranking code — call the same functions.
- [ ] **13.4 — Where it lives in the UI.** A new **"Search"** page in
  the sidebar, between Dashboard and Downloads. Dashboard is
  playlist-centric and already the most crowded page in the app;
  Downloads is a status view. A dedicated page also gives the results
  table room, which the Duplicates/Sharing tables show this app needs.
- [ ] **13.5 — The page.** Two fields (Artist, Title) + Search, running
  through `run_worker` with the standard busy/status treatment (a real
  SoulSeek search takes 20-45s — `client.py:78` — so a visible busy
  state is mandatory, not optional). Results table: Username, Filename,
  Format, Bitrate, Size, Locked, Score, sorted by the same `_sort_key`
  ranking. One primary **"Download best"** button (the automatic
  best-with-fallback path, the headline feature) plus a per-row
  "Download this one" for an explicit override. Reuse
  `theme.cell_widget` from 10.2 for those row buttons, and set the
  column widths — do not repeat the P4 mistake on a brand-new table.
- [ ] **13.6 — CLI parity.** `seeker search "<artist>" "<title>"
  [--download]` — listing by default, downloading the best with
  `--download`, matching how every other action in this app has both
  surfaces.
- [ ] **13.7 — Guardrails.** A manual track must not appear in playlist
  track counts, `check`, or the next-step CTA logic; verify
  `dashboard_service` and `_fetch_next_step_facts` are all

- [ ] **13.8 — Tests.** Service-layer tests for: no destination

## One real defect found in the new work

- [x] **R1 — `_build_info.py` is tracked, and `build_dmg.py` never
  restores it, so every real build permanently dirties the tree.**
  `git ls-files` confirms `src/seeker/_build_info.py` **is tracked**
  (with the committed `GIT_SHA = "dev"` fallback — good, a fresh clone
  imports fine). But `.gitignore:18` lists it, and `git check-ignore`
  confirms that entry does **nothing**: git never applies ignore rules
  to an already-tracked file. `packaging/build_dmg.py:62` calls
  `_write_build_info()` and there is no `finally`, no restore, no
  `skip-worktree` anywhere in `packaging/`.

  Failure mode, and it is the exact thing item 81 exists to prevent: run
  a real `.dmg` build → the tracked file now holds a real SHA → the tree
  is dirty → the next commit sweeps it in → from then on every dev run
  reports a build identity naming the *previous* commit. A wrong SHA is
  worse than the static `0.1.0` it replaced, because it looks
  authoritative.

  Pick one and implement it properly:
  1. **Restore in a `try/finally`** in `build_dmg.py` — read the
     original bytes before `_write_build_info()`, write them back after
     PyInstaller returns, including on failure. Simplest, keeps one file.
  2. **Split generated from fallback** — `build_dmg.py` writes an
     untracked `_build_info_generated.py`; the tracked `_build_info.py`
     does `try: from ._build_info_generated import *  except ImportError:
     GIT_SHA = "dev"…`. Cleanest, and the gitignore entry then actually
     works.

  Option 2 is preferred. Either way, **delete or correct the misleading
  `.gitignore:13-18` comment**, which currently asserts a protection
  that does not exist. Add a test asserting the tracked
  `_build_info.py` still reads `"dev"`, so a real SHA can never be
  committed unnoticed.

  **Resolved — option 2 implemented.** `build_dmg.py` now writes
  `src/seeker/_build_info_generated.py` (genuinely gitignored, never
  tracked); the tracked `_build_info.py` is a pure
  `try/except ImportError` fallback shim, never itself written to.
  `.gitignore`'s comment corrected. New `tests/test_build_info.py`.
  `mypy --strict src/` clean, full suite green (2 pre-existing,
  unrelated failures reproduced identically on a clean pre-fix
  checkout — see `docs/TASKS.md`'s R1 entry). See CLAUDE.md roadmap
  item 83.
